### Authentication refusal

The extractor could emit both `authAction=decline_authentication` and
`phoneConfirmation=no`. The runtime prioritized phone rejection and incorrectly
offered email authentication. Explicit authentication refusal now closes protected
work unless persisted state proves the user is rejecting an active phone association.

### Conversation continuity

The reproduced Carina and María Isabel failures were not proven races and their recent
conversation was not generally missing.

- Carina: a valid purchase request was discarded when `authAction` was null. Null now
  normalizes to `none` instead of erasing the request.
- María Isabel: a short misspelled continuation could yield empty extraction. Typed
  support acknowledgements now save a compact canonical `conversation_summary`.
  When history retrieval is empty but that canonical informational summary exists, a
  narrowly scoped composer receives only the summary and a turn-specific clarification
  constraint. There is no second `support_anchor`, raw history replay, or global rule.

Do not reintroduce a generic conversation-restart workaround or another parallel
memory store. Empty extraction must be interpreted using typed plan/history evidence;
it must not automatically mean a new conversation.

### RSVP event timestamps

The Agent API supplied localized server values such as `10/10/2026 20:15`, but the
validator accepted only ISO values and discarded the event date. The validator now
accepts and preserves valid `DD/MM/YYYY`, `DD/MM/YYYY HH:mm`, and
`DD/MM/YYYY HH:mm:ss` values without constructing `Date` or applying any timezone
offset. The server is authoritative. Do not restore the old Lima/UTC conversion.

### Disclosure and prompt discipline

- Null currency is never inferred.
- Approved summaries do not disclose payment method unless requested.
- Pending guidance may mention the recorded payment method only when needed to ground
  the indexed validation policy.
- Raw API and knowledge-base responses are parsed, reconciled, and projected before
  any model sees them.
- No bank data, vouchers, gateway messages, tokens, raw payloads, or internal comments
  may enter model context.

## Remaining failures, classified by cause

Do not treat these classifications as permission to patch blindly. Confirm each one

### A. Development write isolation conflicts with live-case expectations

These cases expect successful or rejected mutations, but the test-only Lambda correctly
blocks real customer writes. The runtime reaches the relevant tool; the environment
returns `Customer writes are disabled in this environment.`

- `live_behavior.otp_nondelivery_auto_resends_once`
- `live_behavior.otp_number_words_are_verified`
- `live_behavior.repeated_otp_failure_preserves_gift_query`
- `live_behavior.rsvp_state_reversal_ends_confirmed`

Required direction: design an isolated, explicitly simulated write-capable evaluation
gateway/fixture that cannot address real customers. Keep the development deployment's
real write policy disabled. Never fabricate a successful resend or RSVP write in normal
runtime code. Audit how the live fixtures select gateways and how the capability
manifest represents simulated versus real writes before implementing.

### B. Typed state/routing defects

- `live_behavior.otp_not_received_requires_response`

    `1`, and protected work remains pending.

    instructions.

    outcome from persisted counters, protected request, and absence of an extracted OTP.
    Do not use keywords and do not add a global prompt rule.

    decision while preserving explicit no-change and already-pending behaviors.

    expected current record is pending.
  - Inspect gateway status mapping, `mergePhonePurchase`,

## Audit and refactor sequence

### Phase 1: establish evidence and ownership

- Build a table for all 59 cases: route, extraction result, persisted state, calls made,
  canonical reconciled result, exact model-visible projection, prompt bytes, tools,
  renderer, output, hard assertion, semantic expectation, and failure category.
- Trace where each piece of model-visible text originates. Flag duplicates,
  contradictions, raw/unreconciled fields, impossible branches, and unrelated tools.
- Record baseline serialized instruction/input bytes and tool count by route.
- Use read-only subagents for separate bounded audits: authentication/OTP, purchase
  reconciliation/projection, RSVP, and prompt/tool construction. The primary agent must
  integrate and verify their findings.

### Phase 2: repair the evaluation environment

- Specify a test-only simulated write boundary for OTP and RSVP.
- Prove it cannot invoke real write endpoints, cannot be selected by the production
  composition root, and is reflected truthfully in the capability manifest.
- Update only cases whose present expectation contradicts the real dev write policy.
- Keep hard structure and `text_semantic` with `requireJudge: true`.

### Phase 3: fix deterministic state and reconciliation

In this order:

1. OTP non-delivery exhaustion from persisted typed counters.
2. RSVP declined-state one-change policy.
3. Kiara status reconciliation.
4. Joaquin safe-read-before-unsupported-mutation behavior.

For each fix, add or retain an offline deterministic twin and a separate entry in
`evals/live-behavior-coverage.yaml`.

### Phase 4: minimize canonical reply evidence

Fix order/cart distinction, mismatch provenance, missing event association, unique
record certainty, pending-transfer continuity, and clarification evidence leakage at
the typed projector/renderer boundary. The reply model should receive only the chosen
canonical result and the relevant action/outcome. Measure that unaffected routes do
not gain prompt bytes or tools.

### Phase 5: audit prompts and architecture

Only after characterization tests exist:

- Inventory every model call and its stable prefix, dynamic sections, schemas, tool
  definitions, and duplicated history.
- Separate model responsibilities: extraction interprets the turn; deterministic code
  validates capabilities and state; reconciliation selects trusted facts; rendering or
  the reply model communicates the already-selected result.
- For FAQ, test whether the event-planning state machine adds no decision value. A
  simpler FAQ lane is acceptable if it preserves injection boundaries, retrieves only
  indexed knowledge, reconciles it with typed endpoint evidence when both are relevant,
  and returns to the existing plan without erasing state.
- Candidate module boundaries, subject to evidence:
  - `ConversationContinuityPolicy`
  - `InformationAuthStateMachine`
  - `PurchaseEvidenceReconciler`
  - `PurchaseReplyProjector`
  - `RsvpDecisionPolicy`
  - `CapabilityBoundary`
- Prefer removing duplicated conditional prompt text over moving it. Do not serialize
  the full capability catalog, raw API responses, or every failure mode into ordinary
  turns.
- A major refactor must preserve behavior with characterization tests, be split into
  atomic commits, and be evaluated incrementally in development.

### Phase 6: validation and deployment

For every conversational change:

1. Run focused offline tests, typecheck, lint, prompt audit, and prompt-size/relevance
   checks.
2. Register a distinct behavior-change entry in
   `evals/live-behavior-coverage.yaml`.
3. Build one content-addressed artifact and deploy it only to
   `recap-agent-runtime-dev` with CloudFormation.
4. Run the focused live cases.
5. Run the complete mandatory live suite with no skips, missing judge, evaluator error,
   empty selection, or failed hard expectation.
6. Record the artifact and run IDs in `docs/implementation-log.md`.

After development is genuinely validated, stop and ask Leonardo before production
promotion. Production must receive the exact already-validated development S3 object;
do not rebuild it. Verify matching `CodeSha256`, preserve production secrets/tables/
URL/webhook, and run read-only smoke checks.
