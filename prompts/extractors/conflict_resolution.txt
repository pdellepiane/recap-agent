Resolución de conflictos:
- Conserva el valor actual del plan si el nuevo mensaje no lo corrige ni lo reemplaza.
- Si el usuario corrige explícitamente un dato, reemplázalo.
- Si el nuevo mensaje es ambiguo, no sobrescribas el valor actual.
- No elimines datos útiles solo porque el usuario no los repitió.
- No elimines categorías de vendorCategories solo porque en este turno el usuario se enfoque en otra.
- Si el usuario cambia una preferencia por una restricción dura, mueve la información al campo correcto.
- Si el usuario menciona opciones por orden, como "la primera", "la segunda" o "la primera y la tercera", llena selectedProviderHints con cada índice textual resoluble.
- Si el usuario menciona características de opciones ya vistas, como "la de queso", "la del coro", "la de violín" o "la música en vivo", busca esas características en la shortlist del plan base y llena selectedProviderHints con cada proveedor correspondiente si hay coincidencias claras.
- Si el usuario menciona varios servicios pero aclara por cuál quiere empezar, conserva todos en vendorCategories y usa activeNeedCategory para el foco actual.
- Si el usuario confirma uno o varios proveedores ya vistos y además pide avanzar con otra categoría, no pierdas la selección previa: llena selectedProviderHints y usa activeNeedCategory para la nueva categoría si queda clara.
- Si el usuario confirma una o varias opciones previas y pide "qué falta", "qué sigue" u otra necesidad, no trates esa pregunta como refinamiento que borra la selección; conserva selectedProviderHints y actualiza activeNeedCategory solo si aparece una nueva necesidad explícita.
- Si el usuario pregunta por fecha, hora, lugar, invitados, anfitriones o confirmación de asistencia de un evento específico asociado a su cuenta, crea `informationRequests.kind=associated_event` y deja `actionIntent=null`.
- Si pregunta por una orden, regalo comprado, pago, dedicatoria, tarjeta física, envío o agradecimiento propios, crea `informationRequests.kind=purchase`. No lo conviertas en FAQ y no afirmes que no podemos ayudar.
- No conviertas una actualización no accionable sobre un regalo en `actionIntent=cerrar`. Cerrar se refiere a finalizar el plan de proveedores o enviar solicitudes a proveedores seleccionados, no a que una persona diga que ya compró o envió un regalo.
- La ausencia de número de orden no es ambigüedad: es un dato opcional. Si la consulta personal está clara, crea la solicitud `purchase`, deja `orderId=null`, usa `ambiguity.status=clear` y permite que el flujo solicite el correo para revisar compras recientes.
- La ausencia de un aspecto más específico tampoco es ambigüedad. Para “estado de mi pedido”, “pedido específico”, “orden propia” o una compra propia sin más detalle, usa `resource=orders`, `aspects=[summary, payment_status, shipping]` y `ambiguity.status=clear`.
- Si el nodo actual contiene solicitudes informativas pendientes, interpreta respuestas breves de autenticación, selección o seguimiento dentro de ese contexto y conserva la capacidad pendiente adecuada.
- Si `information_state.authentication_status=code_requested`, una indicación semántica de que el código no llegó debe conservar la solicitud protegida pendiente y usar `authAction=report_otp_not_received`. Una petición de otro código usa `resend_otp`; una corrección del correo usa `change_email`; un código escrito por la persona usa `provide_otp`.
- Si no existe contexto suficiente y el mensaje es una referencia breve como "el horario", "el dato" o "la dirección", usa `ambiguity.status=ambiguous`, `informationRequests=[]` y una sola `clarificationQuestion`. No inventes el referente.
- Si el usuario pregunta si puedes leer una fotografía, captura de pantalla o imagen, crea una consulta FAQ sobre esa capacidad. No uses solicitar_humano salvo que también pida explícitamente hablar con una persona.
- Si pide retiros, finanzas del anfitrión, disputas de propiedad o modificar una compra, no lo presentes como lectura soportada. Usa FAQ para explicar el alcance general o solicitar_humano si pide revisión humana explícita.
- Si combina preguntas generales, eventos asociados y compras personales, crea una solicitud separada para cada necesidad informativa.
- Si combina una acción de proveedores con consultas informativas, conserva `actionIntent` y `informationRequests`; no elijas una por el usuario.
- Si el usuario pide pausar aunque también dé más información, pauseRequested debe ser true.
- Si el usuario pide reemplazar, sustituir o cambiar una opción por otra (ej: "reemplaza la primera por la segunda", "cambia la selección por otra opción"), usa providerPlanOperations con type=replace_provider y llena removeProvider/addProvider con los títulos o IDs del plan base. No llenes selectedProviderHints en estos casos; el reemplazo se maneja por providerPlanOperations.
