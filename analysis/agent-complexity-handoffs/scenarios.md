# Scenario understanding and proposed ownership

All case IDs below refer to the fixed 18:23 UTC run unless another run is named. “Pass” means that run's expectations passed; it is not a claim of ideal product behavior. Review complete state and tool outcomes before using judge prose as root-cause evidence.

| Scenario and complete context | Observed behavior | Correct behavior and architectural implication |
| --- | --- | --- |
| `live_behavior.purchase_confirmation_carina_request_survives_normalization`: prior campaign identifies the gift event; requests payment confirmation, repeats with gift context, then explicitly asks for recorded status and amount | Clarifies first, prematurely answers status second, correctly answers explicit status third. Same failure in fresh 19:46 replay | Preserve status-versus-document ambiguity until resolved; purchases specialist owns this distinction. Runtime must not erase it |
| `live_behavior.mailbox_issue_deferral_and_clarification_preserve_support`: greeting, full registered mailbox, deferred submission, misspelled clarification | Four-turn support continuity passes, including fresh replay; answers repeat that context is retained | Support owner should preserve issue and pending material, avoid OTP and false transfer. Passing continuity still leaves a product question: does the response advance resolution? |
| `live_behavior.ambiguous_confirmation_clarifies`: recommendation state, more than one plausible provider/action, brief affirmative | Earlier run clarifies generically but fails expected node; fresh replay asks which provider or action and passes | Planning owner retains exact pending question and candidates. Bare affirmative is not sufficient to pick a provider |
| `live_feedback.token_seeded_close_flow`: selected provider; close request; name, email, phone; explicit final dated submission | Earlier run repeats confirmation after explicit request; 19:33 run writes twice despite a passing final-text judge | One planning owner and guarded effect executor; contact capture cannot authorize submission. Validate all turns and receipt counts |
| `live_behavior.wedding_planner_location_completes_search`: progressively supplies event type, attendee range, location | Four-turn planning reaches search; passes | Keep planning state across turns. Do not split interview and search into unrelated agents |
| `live_feedback.token_fresh_multifront_stays_multi_need`: one event, several distinct provider needs | Multi-need route passes | Shared event plan remains primary; no agent per provider category |
| `live.faq_from_recommendation_node`: asks fee policy before selecting a provider | Grounded FAQ answer; passes | Answer FAQ as a bounded subtask while preserving shortlist and return owner. Existing case covers interruption, not a full later return turn |
| `live_behavior.host_support_allows_explicit_rsvp_switch`: active host-support context, explicitly changes topic to attendance status and forbids a write | Reads attendance without mutation; passes | Hard ownership must permit explicit switch; do not let support state trap the user |
| `live_behavior.roberto_verified_unique_rsvp_writes_once`: unique verified invitation and explicit attendance request | Attendance path passes | Invitations specialist owns interpretation; deterministic identity, target, authorization, and write deduplication remain shared |
| `live_behavior.rsvp_missing_action_requires_explicit_decision`: attendance context without a new explicit decision | Hard semantic expectation fails while response asks about changing current nonattendance | Inspect receipt and literal wording separately. A new agent does not replace explicit-action checks |
| `live_behavior.otp_terminal_handoff_unknown`: rejected code followed by uncertain human-help outcome, then further code-related replies | Three replies truthfully preserve uncertainty; no automatic repeated write; passes | Shared effect state must distinguish failed, unknown, and successful outcomes. Silent internal handoff differs from requesting human help |
| `live_behavior.accountless_event_answer_precedes_remaining_private_auth`: some public/phone-scoped work ready, protected work blocked | Passes | Retain mixed tasks; answer ready portion with one next step. A single-owner design still needs bounded multi-task handling |
| `live_behavior.image_conversation_continuity`: image interpretation followed by a contextual follow-up | Passes in fixed run after earlier failures | Image is evidence attached to the active task. Preserve caption and prior interpretation; never treat visible receipt text as verified payment |

Proposed cross-owner acceptance additions: planning → FAQ → provider selection; purchase clarification → attendance status → purchase clarification resume; image caption with a purchase question; support → explicit RSVP switch → support resume; mixed FAQ and protected purchase with only one task ready; interruption after quote authorization but before an uncertain receipt. These are proposed experiments, not implemented cases or coverage registrations.
