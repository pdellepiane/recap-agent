# Candidate selection population

The earlier 24-case targeted run is unchanged. For a future run, six new cases use two previously observed public catalog queries: birthday catering in Lima (three earlier repetitions each returned seven candidates) and wedding photography in Lima (three earlier repetitions each returned ten). Each case asks the user to select the second displayed provider, checks at least two returned candidates, compares the chosen ID with the second uniquely identifiable delivered option, and checks no unrelated effects. The event types and categories are limited to these two; this does not establish performance across all event types or provider categories. The public catalog can change, and a returned candidate is not proof it was displayed.

Predefine a separate eligibility count: a selection comparison is eligible only when at least two unique options are actually identifiable in the delivered response with linked evidence. Preserve raw hard-gate results and report ineligible/unassessable cases explicitly, including their reasons. The current harness marks an unassessable comparison as a hard failure; do not silently relabel or exclude it from the original hard-gate denominator. Report the conditional eligible comparison as an additional descriptive analysis with its own denominator. Avoid retries selected after seeing outcomes. Simulated effects cannot establish external delivery.

Cases `live_behavior.final_second_birthday_r1`–`r3` and `live_behavior.final_second_wedding_r1`–`r3` are prospective candidates only. No run, freeze, or claim of independence is implied. Their inputs intentionally match prior queries, making this follow-up validation rather than a held-out generalization test. Preserve prior run identities and scores separately; freeze the final full protocol and deployment before execution.
