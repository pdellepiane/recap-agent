# Testing and validation

**Evidence cutoff:** 30 September 2026, America/Lima. The final targeted run is timestamped 1 October in UTC. This is the current testing contract; dated reports retain their original results.

## What the tests establish

The live behavior suite checks observable product obligations. A reply that sounds convincing does not establish that an action happened. Independent backend records, effect receipts, persisted state and delivered facts supply the evidence.

| Obligation | Hard evidence |
| --- | --- |
| Authorization | Caller identity and account scope, OTP/login outcomes, cross-account isolation, trusted-phone gating and fail-closed access. |
| Effects | Requested entity and polarity, attempted/successful/replayed writes, no writes during read-only turns, no duplicate submissions. |
| Facts | Returned totals, dates, payment/attendance states and other requested backend values; deterministic assertions rather than judge votes. |
| Failures | Honest failed/unknown outcomes, retryable busy responses, correlation and tracking, no silent or invented success. |
| Contracts | Validated API/schema boundaries, trace and receipt emission, money/reconciliation arithmetic, malformed-input handling and external backend boundaries. |

Semantic judge votes, style/tone/wording pins, internal node transitions, mandatory read-tool calls, token counts and prompt byte budgets are excluded from the live behavior gate. Exact text checks are appropriate only for independently established values or contractual URLs. They must not prescribe a conversational sentence. Prompt and cost measurements remain diagnostic evidence, separate from the behavior verdict.

These checks establish the tested obligations, not universal conversational quality. Human transcript review can assess whether an answer is understandable, complete and useful; its observations should identify missing facts, incorrect actions or concrete failures rather than become a preference-based gate. Every delivered conversational sentence remains generated by the model for that turn.

## Layers and coverage

Offline tests validate deterministic invariants and use synthetic gateways or runtime doubles to isolate failures. They do not prove live model behavior. Live cases invoke the deployed development Lambda with versioned fixtures and reconstruct complete interactions, including relevant history and seeded state. Fixture-backed live success proves the deployed path against that world; it does not certify the production marketplace or the external WhatsApp adapter.

Every behavior change receives a separate entry in `evals/live-behavior-coverage.yaml`, even when it reuses an existing case. Active entries must reference mandatory `live_behavior_regression` cases with hard objective assertions and no semantic judges. Retired entries state the retirement reason and preserve their original case IDs; retirement is not equivalent replacement coverage. Run `tests/live-behavior-coverage.test.ts` before handoff.

The current live suite contains **46 cases, 185 turns and 329 hard assertions**, with no semantic judges.

## Effect counts and negative controls

A `fixture_effect_count` expectation with `turnIndex` checks the delta for that turn, not the cumulative conversation total. An action turn can require one successful write while a later recall or thanks turn requires zero new attempts, successes and replays. A cumulative prior receipt must not be mistaken for a duplicate effect.

Six later-turn count expectations were corrected on that basis. Their original action turns still require the original write. The offline check in `tests/eval-snapshot-fixture-effects.test.ts` proves that all six corrected contracts reject an injected extra write. The OTP and RSVP regression twins also fail when their respective runtime fixes are removed. These controls demonstrate detection of material violations rather than merely asserting that current output passes.

## Execution and handoff

1. Define the correct behavior and preserve the complete interaction and authorized fixture world. Add hard assertions and an offline twin when applicable; register the change.
2. Run checks relevant to the changed contracts. Keep failures visible and investigate whether they are product defects, incomplete fixtures or demonstrably wrong oracles.
3. Deploy Lambda-impacting changes to development using `se-dev` in `us-east-1`, after STS confirms account `684516060775`. Documentation-only changes do not require deployment.
4. Freeze explicit case IDs, fixture and expectation versions, deployment identity and paid-run budget. Run only that targeted panel:

   ```bash
   AWS_PROFILE=se-dev AWS_REGION=us-east-1 npm run eval:behavior-live -- \
     --case live_behavior.otp_number_words_are_verified \
     --case live_behavior.rsvp_explicit_mutation_targets_requested_event \
     --label selected-behavior-validation
   ```

   This illustrates selection syntax; it is not standing authorization to execute paid cases. Never run an unfiltered live gate, expand a frozen panel or retry semantic failures without a new user instruction.

5. Read the final `report.json` and manifest, not progress labels. The progress label `ok` means execution completed; it does not establish that hard assertions passed. Missing turns, uncertain execution, absent required receipts or unverified/mixed deployment identity invalidate acceptance.
6. Preserve all results and run IDs. After an infrastructure interruption, establish execution completion before replaying a possible mutation, restore access through `aws login --profile se-signin`, and verify the required account/artifact. Record any subsequent validation separately; never overwrite the interrupted run.
7. Handoff the exact tested scope, artifact and costs, all remaining failures, contract changes and negative-control evidence. A passing subset or a source archive is not a production promotion or a clean Git release.
