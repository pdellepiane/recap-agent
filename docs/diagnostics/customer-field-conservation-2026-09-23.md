# Customer field conservation inventory

This inventory is checked against the current gateway schemas and mapping code. The profile is assembled before extraction by `InformationOrchestrator.prepareCustomerContext`; `projectCustomerContext(snapshot)` is the only customer-profile serialization boundary. Owner B passes that same projection as `customerContext` to the extractor and reply request. The profile arrays contain one record body per `(authorized scope, source, record type, stable ID)`; event summaries carry `orderIds` references instead of copied order bodies.

## Source coverage, pagination, and read behavior

Preparation reads all authorized purchase roots and event roots before extraction. Known linked event IDs are deduplicated by authorization scope and ID, then fetched through the existing detail route using a four-worker queue; concurrency is bounded, total queued records are not. The turn-local read metrics report total calls, peak concurrent calls, and per-operation counts. Identical root/detail calls are single-flight within the turn; a new actionable turn prepares a fresh snapshot.

The current typed contracts and wire parsers for `/orders`, `/gift-purchases`, `/guest/orders`, `/guest/gift-purchases`, `/guest/events`, `/event`, `/user-lookup`, and `/conversations/messages` declare no continuation token, page number, total-page count, or pagination-exhausted flag. The adapters therefore preserve every returned record, set `paginationExhausted` and `historyLimit` to `null`, and do not claim page exhaustion. A newly returned unknown continuation key is reported by the value-free wire-key diagnostic; it is not guessed or followed without a documented gateway contract. Missing authorization yields explicit unavailable sections and zero protected reads. Empty, not-found, unavailable, failed, and partial sources remain distinct; a failed source cannot erase facts already fetched from another source.

## Explicit field exclusions

| Wire/domain field | Reason |
| --- | --- |
| API keys, account tokens, OTPs, session credentials | Execution secrets. They are never customer facts and are excluded before profile construction. |
| `/user-lookup.user.id` | Internal account key. It is not needed to identify the customer conversationally; backend-grounded name/email/phone are used within authorization scope. |
| `increment_id` / `customerTransactionNumber` | Existing internal transaction-reference authorization rule; the full stable order record remains, but this identifier is removed from model projection. |
| `payment.payment_id` | Internal payment identifier; payment method, amount, status, time and destination evidence remain. |
| raw voucher URL/image | Private resource location; `voucherProvided` indicates presence without exposing the URL. |
| `admin_comment` / `adminComment` | Private operator-only note. |
| Unknown future wire keys | Not blindly copied into prompts. Safe diagnostics report endpoint and field path without values, requiring explicit schema and inventory review before mapping. |

No conversationally irrelevant customer fields are excluded. In particular, order and payment amounts, payment facts and destination, carts, all returned gifts/items, card physical status, thanks, event amounts/counts/details, dates and older records survive independently of the extractor's route, resource, references, question or prior extraction correctness.
