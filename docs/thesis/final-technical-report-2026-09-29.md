## 1. Purpose and delivered system

Recap Agent is a serverless conversational service for Sin Envolturas. It helps a customer plan an event with multiple provider needs, retrieve public knowledge and authorized customer records, inspect invitations and purchases, and perform verified actions such as RSVP or provider quotation. The core accepts normalized turns from a channel adapter; WhatsApp transport, sender identity, webhook acknowledgment, and outbound delivery belong to that adapter. The local terminal exercises the deployed Lambda contract.

The delivery is a TypeScript application using the OpenAI Agents SDK, Spanish prompt files mapped to flow nodes, AWS Lambda, DynamoDB, CloudFormation, the Sin Envolturas provider and Agent APIs, and OpenAI vector stores. The `src/core`, `src/runtime`, `src/storage`, `src/lambda`, `src/terminal`, `src/evals`, `src/provider-sync`, and `src/knowledge-sync` directories separate domain state, conversation, persistence, transport, evaluation, and synchronization. `infra/cloudformation/stack.yaml` defines the runtime; `infra/provider-sync.yml` and `infra/knowledge-sync.yml` define auxiliary synchronization.

## 2. Architecture and turn lifecycle

1. The Lambda handler validates bearer authorization and a typed request. It keeps a correlation ID on every response. For authenticated pre-validation failures it logs only payload structure, byte count, hashes, and phone-parse outcome, without raw customer values.
2. The service loads the channel-scoped plan and coordinates the turn with a lease/fencing mechanism. Existing conversation context and persisted media references can be resumed.
3. Before extraction on an actionable customer turn, the information orchestrator prepares a canonical authorized customer profile. It reads available order, gift, guest-event, user-event, and event-detail roots. Parallelism is bounded, but record age and first-N limits do not discard authorized records. Every section carries source, scope, fetch time, completeness, pagination, and failure state. A declined authentication request blocks protected reads.
4. Structured model extraction identifies semantic tasks and possible actions. Typed state validates the extracted proposal, preserves established context, and gates tools and effects. Raw keyword matching does not decide a conversational route.
5. The runtime executes eligible reads and guarded effects. RSVP writes bind the requested event and guest identity, use phone-scoped authorization, and reconcile backend receipts before reporting success. Provider planning keeps multiple needs in one persisted event plan.
6. A typed request compiler selects only relevant Spanish instruction modules, evidence sections, and executable tools for each model call. Serialized instruction and input bytes are measured. The final conversational sentences are generated by the model for that turn; code validates structure and receipts but does not insert canned prose after generation.
7. The resulting plan, trace, usage, and performance record are persisted. The channel response contains only delivery data unless the client explicitly requests CLI diagnostics.

The main model stages presently include a structured extractor, reply composition, and a response classifier where required. The September lean-conversation plan proposes further consolidation; its future three-owner architecture must not be presented as fully implemented. The working runtime already uses owner- and task-specific prompt projection, but still contains existing stages and node-oriented flow.

## 3. Functional changes since the partial delivery

### 3.1 Complete customer information and access control

The canonical profile is assembled independently of extractor-selected routes, aspects, and relevance hints. The same authorized profile reaches extraction and reply, while operational lookup choices affect actions rather than erasing facts. Purchase and gift records retain per-source provenance, payment and fulfillment fields, source conflicts, and explicit incomplete-source status. A source failure is not rendered as an empty result. Account and trusted-phone scopes remain distinct; an OTP transition can add newly authorized account records without losing phone-scoped records. Access-control secrets, internal references, and records beyond the caller's scope are excluded.

The information flow supports FAQ, associated events, orders, and gift purchases in one typed read-only turn. Customer transaction references can resolve an exact record; unresolved multiple candidates remain distinct. Gift fulfillment differentiates physical shipment, account credit, payment status, and unknown shipping. Commission responses are grounded in the retrieved full article and calculator link, with outcome-specific guidance selected only for commission questions. Knowledge scraping and retrieval preserve source fidelity and citations.

### 3.2 Invitation, RSVP, and local time

RSVP decisions preserve event and guest identity across candidate reads, explicit mutations, companion requests, and backend receipts. Exact numeric event-ID binding was added after a development gate exposed a name-only match. Rejected companion effects are represented separately from the guest's own attendance. A refusal or failed effect cannot be presented as a successful write. Event-time projection converts a timestamp with an explicit offset into the verified event time zone, handles date rollover, and avoids inventing an hour for date-only values. Read-only associated-event answers now receive this projected local time as well.

### 3.3 International sender identity and observability

Incoming phone parsing accepts assigned international country codes with an explicit `+` and retains exact historic national-length rules for `+1`, `+51`, and `+52`. It does not infer a country from language or event location. The September Sinar investigation found an inbound decline stored in the Agent API without a matching runtime record. A nearby 400 response lacked enough identity evidence to attribute it to that message. The runtime now echoes and logs a bounded `x-recap-correlation-id`, and authenticated invalid requests receive a protected structural capture. The external WhatsApp adapter still owns trusted E.164 sender derivation and correlation-header propagation; that implementation is outside this repository.

### 3.4 Provider planning, media, and continuity

The event plan can hold multiple provider needs and selections. Provider search combines API-backed candidates and vector search, then enriches results before the reply model sees them. Conversation continuation preserves open tasks, resolved facts, and relevant image references. When an image URL cannot be accessed, the model receives an explicit availability outcome and can answer from other authorized records without claiming to have seen the image. Human handoff and support status are driven by actual receipts, not a scripted answer.

## 4. Tests and evaluation — WIP

**Status: work in progress.** The test section is intentionally not closed in this documentation delivery. The owner will finish test review and any remaining validation after the documentation update. Results below are the latest recorded evidence and should not be read as final test acceptance.

The project has offline tests, a typed live-case schema, stored fixtures, mandatory `live_behavior_regression` cases, a behavior-coverage registry, structural assertions, and hard semantic judgments. New behavior changes receive separate registry entries. The current operating rule is to deploy Lambda-impacting changes to development, then run only an explicitly selected and frozen targeted live panel with a paid-run budget. A semantic failure is not retried or silently relabeled. Earlier full-gate runs remain historical evidence, not a current instruction to run another full gate.

The panel combined 28 critical cases with 15 RSVP, phone, time-zone, and continuity cases. The two previously failing time-zone cases passed. All checked fixture-effect counts passed. The eight failures include two carried from the previous panel, two previously passing cases with new semantic failures, and four cases introduced by the wider selection; see `docs/implementation-log.md` and `docs/diagnostics/2026-09-29-critical-feature-gate-audit.md` for case-level evidence. These numbers describe that exact development artifact and selected cases only.

The offline suite was not green at the final gate: the recorded audit reported **118 failed and 2,127 passed** after the last local-time projection. The implementation log documents unchanged legacy assertion clusters and targeted passing safety/effect tests. A passing targeted panel does not erase those failures. The remaining test reconciliation, case disposition, and any later targeted validation are **WIP**. No later blanket acceptance result is recorded here.

## 6. Limits and next ownership

- Tests and evaluation are **WIP**. Eight selected live semantic cases remained open at production promotion, including host-declining state consistency, commission citation behavior, companion response wording, reminder meaning, response-date claims, ambiguous RSVP routing, and closing nuance. Their exact disposition is in the dated implementation log.
- The full offline suite still has failures; its review remains WIP and it must not be described as a passing release gate.
- The external adapter must derive a trusted international phone, forward the correlation ID, and reconcile stored inbound messages that never reached the runtime. The Sinar stored decline was already reflected as declining by the downstream API, so a blind replay would risk a duplicate.
- Backend pagination and undocumented history limits remain explicit unknowns in the customer profile. The runtime preserves all records returned by authorized roots, but cannot claim that an API returned all historical data without source evidence.
- The lean-conversation acceptance contract remains a direction for further architectural cleanup. The current report documents the implemented state and the measured release evidence.
