## Invariants and runtime checks

### I1 — Complete authorized RSVP candidate set

For a phone-scoped RSVP turn, collect every authorized event/invitation candidate returned by the complete customer profile and phone event lookup, retaining each source's status (`success`, `empty`, `failed`, `deadline`) and provenance. No first-N, age, name, or relevance filter may delete a candidate. Reconcile only by validated `eventId + guestId`; a same-name match is never identity. If a source is incomplete, set `coverage=partial` and preserve which source failed. Add a pre-compose assertion that the output candidate IDs and count equal the authorized reconciled set, except for a verified exact duplicate. Test complete and partial reads.

### I2 — Per-invitation state is conserved

For each candidate, preserve `willAttend`, `hasResponded`, event identity, guest identity, source and freshness. `willAttend=true/false` determines attending/declining; `hasResponded` alone does not erase a host-set decision. A missing detail read is `not_read`, a failed read is `read_failed`, a read with no attendance is `not_present`, and an actual undecided attendance is `pending`; none may be projected as a blanket assertion that a known state is unavailable. The canonical customer profile may already provide the state; reuse it. When a phone-only candidate still needs details, fetch details for **all** authorized candidates (bounded concurrency, no record-count cutoff) or use an authoritative batch endpoint. Read cost is measured; completeness wins over an arbitrary one-detail cap. If a detail cannot be obtained, expose per-candidate uncertainty and the source failure explicitly. A pre-compose conservation test must compare every known source state to the serialized reply input, including same-name/different-guest and host-set decline cases.

### I3 — Selection and effect truth

No RSVP mutation until one unique candidate is identified by validated identity. An explicit current-turn decline on a unique unanswered invitation may submit once without another confirmation. After writing, use the existing verified fresh read/receipt; report success only when verified. Multi-candidate ambiguity yields one focused selection request and zero writes. A read-only status question yields zero writes. Pre-compose checks compare selected guest/event IDs, intended action, attempt count and verified final state. No prompt instruction can override a failed or missing receipt.

### I4 — Inbound delivery is observable

The WhatsApp adapter must send a trusted international phone or fail before forwarding with a typed delivery error. Normalize only from a channel-verified country/number pair; never guess `+51` from message text or arbitrary digits. Instrument a privacy-safe correlation key spanning adapter message ID, Lambda request ID, validation outcome, classifier action, RSVP lookup and effect receipt. An incoming explicit decline with a valid trusted phone must either reach a delivered model reply/effect or have a traceable typed failure. Distinguish adapter rejection, classifier suppression, no candidate, mutation failure and channel delivery failure. Do not weaken validation just to turn a 400 into a 200.

### I5 — Commission answer is source-backed and complete for the question

Use the synced help-center article as source for fee structure and the US$100 example. Repair the malformed card/PayPal line in the article snapshot through the scraper and sync it with the source; ensure the calculator URL is a usable URL in the delivered reply. For a question about another amount, either obtain a validated authoritative calculator quote for **that** amount, payer, currency, payment method and tax context, or refrain from numerical net/payable claims and give the US$100 example plus calculator. Do not derive exact PEN totals from rounded example percentages. The source/quote projection must state payer, currency, method, amount, tax inclusion, rounding rule/version and completeness. If any prerequisite is missing, project `quote_status=unavailable` rather than partial arithmetic.

### I6 — Model input and output are checked at their boundaries

Before extraction and reply, serialize the complete authorized customer profile independently of the extractor's routes or relevance hints. Attach a compact typed completeness manifest: source names/statuses, record counts, per-record provenance, and missing-source reasons. Assert the manifest against the actual serialized input, not only an intermediate object. For RSVP, include the exact candidate/state projection and mutation outcome; for FAQ, include only the relevant article/quote evidence. If a fact is absent, the model cannot be asked to self-verify it. The model writes the whole reply; a structured factual-claim sidecar may be validated against typed states and effect receipts before delivery. On mismatch, fail the reply and regenerate with corrected evidence once; never patch text or supply canned prose. Record both attempts and bytes. Keep the branch-specific Spanish prompt instruction short and backed by the typed state; add negative controls proving unrelated rules are absent.
