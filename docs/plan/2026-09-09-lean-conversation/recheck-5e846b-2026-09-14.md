## Newly found RSVP integrity defects

### 1. Lease-conditioned receipt write is not reached

`src/runtime/rsvp-effect-executor.ts`: RsvpEffectStore.saveResult interface has four parameters. persistOutcome invokes exactly those four. `src/storage/dynamo-rsvp-effect-store.ts`: transactional lease condition is behind an optional fifth lease argument, so the live executor cannot reach it through that interface. saveIntent also uses a plain conditional Put, not the lease-conditioned transaction claimed by its module comment. A pre-write validateLease callback exists, but a check followed by a separate Put is not an atomic fence.

Decision: fix the existing store seam, not add another executor. Bind the invocation lease to the production store instance or pass it consistently through the typed interface; choose the latter here. Add lease identity to the shared store operation context for intent/result, pass it from the existing inbound.turnLease, and compute Date.now at each Dynamo transaction construction. Use the existing TURN_LOCK condition alongside each receipt write. Keep the callback immediately before the external mutation. The lease does not make HTTP plus Dynamo atomic; retain interrupted-intent read-only recovery. A successful transaction must be observed through the actual executor-to-store path, not a direct five-argument store test.

### 2. CORRECTED: host-set attendance is valid without a guest response

Operator clarification supersedes the earlier diagnosis: hasResponded=false with willAttend=true is possible after a host policy change. The probe was valid, but its interpretation as false success was wrong. Do NOT require hasResponded=true for verification. Verify that the requested willAttend value is returned by a fresh read for the SAME event and guest. hasResponded describes response provenance, not an additional attendance authorization gate. Do not infer who changed the record from these flags alone.

The actual inconsistency is in ordinary read presentation: AgentService.rsvpInvitationState currently returns pending whenever hasResponded=false, even if willAttend is an authoritative boolean. Follow event-identity-review-2026-09-14.md for this correction and identity probes. No new state machine is needed.

### 3. Historical replay can overwrite current profile evidence

Executor replay returns the old outcome with freshRead=false, but nested observed.source remains fresh_read from the original operation. `applyVerifiedRsvpReadToPhoneEvidence` checks status and nested source, not verification.freshRead/replayed. It can apply a historical attendance result to a freshly loaded profile. Service trace also records guest_rsvp before knowing whether a write happened and adds a read tool based on historical readCount.

Decision: only apply observations acquired in this invocation; require freshRead=true and replayed=false before replacing current phone evidence. Historical receipt remains historical outcome data. Report current invocation write/read counts separately from historical receipt counts and only log tool calls actually performed. Replayed current-state questions require a fresh authorized read if current state is being claimed; duplicate delivery must never reissue the mutation. Add restart/replay test where backend attendance changes after the original confirmed result. Assert no second write, no stale profile overwrite and no fictional read trace.

These are product integrity issues, regardless of the passing s11 case. They take precedence over wording work.

## Correct the unavailable-image diagnosis before implementing more reads

Malformed, expired and stale-image inputs contain truthful turn_state.record_checks: lookups_attempted=0 and results_returned=0. These values mean no lookup occurred; they do not mean the backend was searched and empty. The fixture is empty to the evaluator, not evidence read by the agent.

The current request is generally “what is in the unavailable image?” with no identified purchase or requested backend field. No tool can recover missing pixels from an arbitrary unrelated customer profile. Requiring an invented specific missing datum (event name/order number/etc.) is not a justified product requirement. Zero reads is not automatically a defect. Do NOT restore dead image_outcomes.json scripts or blindly read orders merely to satisfy the judge.

Decisions: image/URL requests remain banned. Permit a concise honest limitation when no task can be completed. A question is optional, and only useful if it asks what the customer wants to resolve; do not demand a named datum without an established task. When the user actually asks a purchase question and available authorized records can answer it, perform the relevant reads before asking. Represent not_attempted versus empty_result distinctly. Version oracle revisions under R05; preserve historical results. Add no new media recovery architecture.
