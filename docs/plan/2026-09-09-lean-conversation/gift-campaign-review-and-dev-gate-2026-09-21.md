## Verdict and reproduced findings

The feature is partially correct, not ready to freeze as-is. se_store and credit are now mapped correctly; item-level host choice and no-shipment facts reach model input; campaign-source evidence is consumed; automatic campaign-only handoff is restricted. Raw types in internal model/tool evidence are appropriate. They are not supposed to be exposed as schema labels in customer replies.

P1 — Known gift amounts erased: information-orchestrator.ts shipping-only projection explicitly writes quantity:null, amount:null, rowTotal:null. This is not authorization filtering; it removes already authorized record facts solely because the requested aspect is shipping. The earlier package permitted this excessive narrowing. Restore useful record context while keeping output relevance model-controlled.

P1 — Invalid positional merge: customer-context.ts mergePurchaseItems pairs same-length arrays by position without proving identity. A direct execution with [Sheets/se_store/150, Honeymoon/credit/80] versus the reverse order produces two nameless, amount-less, unknown-type records. Array order is not line identity. Different-length snapshots silently retain the first list without exposing conflict. A type conflict is also not durable: se_store then credit nulls the type, then a third se_store snapshot restores physical as though the conflict never occurred. These are new correctness defects, not wording preferences.

P2 — Customer-facing enum privacy is not directly proven: current serialized tests assert se_store/credit/host_credit exist in spec.input. That proves internal evidence, not that the final model avoids exposing those labels. Existing general style guidance is not targeted proof. Ordinary Spanish 'crédito' is allowed; printing 'type=credit', se_store, host_credit, chosenBy, giftShipmentApplicable, or citing a tool result is not the intended product behavior.

P2 — Campaign duplication and misleading provenance label: buildExtractorCampaignReferenceContext copies body excerpts already present in extractor history, adding reported +415 bytes for the sample. The service also calls any request.eventHint explicit_event_reference although the extractor is allowed to infer eventHint from a campaign. A hint is not proof of explicit customer wording. Do not encode that false distinction.

A limitation to test, not yet a separately reproduced failure: the campaign reply reference still travels in errorMessage/operationalNote, which can be suppressed with images/auth/handoff outcomes. Existing history may retain sufficient context; require mixed-turn serialized proof before claiming the campaign evidence survives all such combinations.
