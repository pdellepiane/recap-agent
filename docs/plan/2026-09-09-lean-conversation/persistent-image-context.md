## Decision and alternatives

Use OpenAI Files as the image storage mechanism, with file references in the existing event plan. Decode validated incoming base64 in memory, upload through Files with purpose vision (as in the official image-input example), explicitly set expires_after created_at + 2592000 seconds (30 days), and retain returned file ID and expiry. No S3, new image database, vector store, OCR service, image-description model or backend change. This stores image bytes at OpenAI; it is not storage-free. Do not persist bytes in DynamoDB, logs, ordinary message history or Lambda temporary files.

Alternatives considered: (a) chain Responses/Conversations state with the image, which is supported but couples application context selection to provider history; (b) store images in S3 and reattach them, which adds storage infrastructure; (c) upload once to OpenAI and reuse file IDs, selected because owners already use explicitly projected context. Do not add a second conversation-state store just for images, and do not treat store:true or recorded response IDs as automatic image memory. Reusing file IDs reduces byte retransmission, not necessarily image token charges.

Retention decision: 30 days from upload, at most five active references per plan, at most two images per model request. Retain original expiry; do not silently refresh it. Clearly report these limits in completion documentation. If a needed image expired, was deleted or was evicted, the model asks for resubmission only when the question cannot be answered without it. No indefinite-memory claim. Existing URL inputs remain supported by the same attachment projection, with their real access limitations; do not expand that optional adapter.

## Event handling and conversational behavior

- Same envelope with image and text: validate both, persist the attachment reference, and process one turn with the text and native image as one user message.
- Image alone: persist its reference before acknowledging successful processing. The established owner uses prior conversation to determine its purpose. If it fulfills an outstanding request, continue that task. If purpose is unresolved, generate one short acknowledgement/clarification. It may recognize a receipt only if visually supported; do not hard-code a receipt assumption or acknowledgement sentence.
- Image then text ten seconds later: the second invocation reloads the same plan and sees the original image reference, even after a cold start or owner transfer. It can answer the new question from that image without asking for it again. No sleep, debounce window, scheduled callback or artificial batching is required.
- Separate events remain separate events; retain existing IDs, timestamps and ordering. No guessed combining based on message content. Reuse the existing per-conversation coordination for upload + reference save so a simultaneous later turn cannot overtake a partially persisted attachment. Use bounded waits and existing retryable transport failures rather than acknowledging an uncommitted attachment.
- No unsolicited visual inventory or OCR summary; no synthetic image-description message inserted into history. An explicit request to describe the image still deserves an answer. All conversational sentences remain current-turn model output. A useful acknowledgement is permitted, not mandatory boilerplate. Thanks does not restart a payment explanation.
- Receipt contents remain user-provided evidence, never authoritative proof of payment approval. Backend status, cart/order separation and relevant customer profile still govern payment answers. Do not ask what the user wants when the existing task already establishes it.
