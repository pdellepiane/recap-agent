## Chosen architecture

Use existing gateways and existing `customer-context.ts`; do not introduce another profile service, model call, agent or persistence system.

The turn sequence is: acquire existing chat lock; load latest conversation and identity; let existing delivery classification handle true suppressed acknowledgments; for an actionable turn prepare the authorized customer snapshot; pass snapshot plus actual current text/history to the extractor; execute permitted explicit actions or additional knowledge queries; update the snapshot with fresh outcomes; pass the same snapshot plus confirmed action receipts to one reply model; save and deliver once.

For any identified customer, the snapshot includes all available customer records regardless of whether the question concerns gifts, RSVP, FAQ or planning. Extraction never selects which customer roots or fields are visible. State controls authorized capabilities and pending effects, not the interpretation of a question or the deletion of context. A pure public interaction with no authorized identity receives an explicit unavailable-identity profile; public help must not be blocked by a new request for identity. Refused/rejected authentication must not be bypassed by profile preparation.

Build a fresh turn-scoped snapshot on each actionable turn using parallel reads under the existing deadline. Reuse identical reads throughout that turn with an authorization-scoped single-flight map; no cross-customer or process-global cache. A new turn refreshes backend facts. No new TTL cache or five-day media store. In-memory concurrency is four simultaneous backend reads, not four total records. Fetch all pages and details reachable through documented customer ownership relationships; deduplicate by `(authorized scope, source, record type, ID)`. Traverse the known customer-to-order/gift/event and detail edges once per ID; do not recursively crawl arbitrary URLs or re-enter cycles. Avoid fetching detail when the documented root response already contains all detail fields. If the backend times out, retain all completed facts and expose unfinished sources/IDs explicitly. Never claim complete data if the deadline interrupted it. Avoid delaying for a new user reply to obtain an ID that a root response already provided.

The complete profile is supplied to both extractor and responder, independent of owner. It is not automatically narrated to the customer. The response model uses the current question to choose what to explain. Remove duplicated representations and instructions to save bytes; the data itself can legitimately make a formerly starved prompt larger.

Canonical record layout uses the existing typed domain objects with one record per source/identity. Preserve customer/account identity as authorized; orders and carts; gifts and all items; payment facts; dedication/card and thanks facts; invitations and guest/host event details; venue/address/moments; campaign messages with source/event relation/delivery metadata; and real action outcomes. All available record dates and older records remain. Do not merge by human names. Preserve source conflicts as alternatives; do not overwrite current facts with a stale reply or unsupported user report.

Define field meaning once in a compact Spanish schema glossary under `prompts/shared/customer_context_fields.txt`: order total versus backend payment amount versus user-reported amount versus remaining balance; physical product versus physical card; credit mechanism versus settlement; raw timestamp plus explicit offset/timezone provenance; campaign sent/delivered/read distinction; existing attendance versus newly verified write. Unknown stays null with source coverage; never zero or absent record. Do not use a glossary full of case names, sample answers, or mandatory recital rules. `payment.amount` means exactly what the backend contract establishes; until verified as settled funds, label it recorded payment amount, never automatically paid/received. Do not calculate a balance from an unverified financial field.

Always exclude API keys, tokens, OTPs and session credentials; these are execution secrets, not customer context. Preserve the existing authorization boundary for internal account/payment identifiers and private operator-only fields. Every omitted backend field must appear in a field inventory with its explicit access/security reason. Bank/payment destination and voucher metadata must be classified from the documented API contract, not erased because extraction did not request them. No silent loss of unknown schema fields: surface an adapter diagnostic for unmapped keys and require mapping review; do not blindly spread credentials or arbitrary internal metadata into prompts.
