# Consolidated profile, contextual inference and useful completeness

Status: audited implementation directive; no implementation or live acceptance claimed. September 15, 2026.

## Binding product decision

Answer the customer's actual need with enough related, grounded information to avoid predictable follow-up questions. Infer the likely referent from outbound campaign context, the conversation, record state and dates near today. Do not require the customer to repeat context the system already has. Build one consolidated, authorized customer profile and serialize each fact once. Explicitly distinguish exhausted sources from sources not checked or unavailable.

This user directive supersedes older campaign-only reference selection, strict asked-fields-only response policies and mandatory clarification whenever several records exist. It does not authorize invented facts, unrelated record dumps, unauthorized disclosure or inferred consent to mutations. All conversation remains generated by the model. No phrase routing, fixed responses, new intent classifier, new agent, confidence-score ladder or hand-built conversational state machine.

Useful completeness is not maximum verbosity: event answers may include date/time, venue/address and attendance when relevant and known; payment answers may include status, amount/method and applicable validation policy. Do not automatically list unrelated carts, all historical events, every null field, or internal completeness metadata. A specific request for only one datum or brevity overrides the default additional detail.

## Audit evidence and limits

Inspected customer-context.ts, information-orchestrator.ts, agent-service.ts, openai-agent-runtime.ts, rsvp-invitation-evidence.ts, rsvp-decision-policy.ts, resolver/extractor prompts and the latest 30-case panel. Catalog inventory covers all 117 cases and 529 expectations, including 64 text containment/non-containment checks. `profile-inference-test-inventory-2026-09-15.json` lists review candidates; it is not a claim that every literal check is wrong. Every expectation must receive a disposition during implementation.

Concrete conflicts:
1. resolveCustomerContextForReply returns null without extracted purchase/event/RSVP signals. Context is assembled late for reply; a misclassified request can be deprived of information needed to recover.
2. hydrateRelevantEventDetails returns without reading when eventHint is absent. That prevents campaign/conversation inference from receiving useful detail unless another path supplies an explicit hint.
3. rankCandidatesByRelevance uses fixed explicit/state scores and descending createdAt/eventDate. Newest is not nearest to today; a distant future event can outrank a nearby event. This code orders records but must not become a deterministic intent selector.
4. groundedRsvpCampaignEvent requires an already-extracted reference and searches admin_campaign text. Its local predicate does not itself check outbound direction. Some surrounding predicates also treat campaign source alone as sufficient. Campaign provenance must be direction-, delivery- and conversation-bound.
5. ReplyTurnEvidence has customer_context, information_results and rsvp_phone_evidence. Single serialization of the profile object does not demonstrate that its underlying facts are not repeated in other blocks.
6. Resolver contract includes asked-aspect-only rules, mandatory missing-currency caveats, rigid clarification and paragraph guidance. Some conflict with useful adjacent information and minimum-turn operation.
7. Latest panel: event follow-up loses date/time intent; declined query asks whether to check the state; payment query becomes a greeting; mixed-language request loses the email part. These are real deficiencies. Delayed-image judge lacks image truth; S07 judge overweights a phrase despite explicit no-change context. Ambiguous selection pins dates, node and counter rather than solely customer outcome.
8. Host-declining fixture was expanded during the prior audit into two identically named/dated events. That is a synthetic ambiguity, not proof of a conflicting same-event attendance record. Correct this fixture rather than forcing the customer to distinguish indistinguishable choices.

No live calls, deployment or tests were run for this audit. Existing working-tree edits must be preserved.

## Fixed decisions for implementers

Reference priority is guidance for the existing model extraction, not a new runtime decision tree: explicit current target/correction; active question and its established entity; relevant delivered outbound campaign; compatible record state and temporal proximity. A new explicit old event always beats a recent campaign or nearby event. A clear topic switch beats previous focus. Multiple competing campaigns are alternatives, not permission to pick the latest blindly.

Use the existing model call to return the grounded target/reference. Runtime validates that referenced IDs belong to the authorized profile; it does not infer intent from keywords. For read-only answers, a strong contextual inference may be answered directly with a naturally identifying event name. If uncertainty remains, offer useful candidate facts and one discriminating question instead of an empty “what do you mean?”. Dates are required when they help distinguish candidates, not in every enumeration.

For mutations, explicit requested action plus one verified event/guest is required. Campaign/context may identify the target, but proximity alone cannot authorize or disambiguate a write. Preserve fresh read-back, effect receipts, lease/replay protection and willAttend precedence. Never require hasResponded=true.

No date cutoff: retain every known historical candidate in the runtime profile/index. Feed current date/timezone and actual event dates to the model. Temporal ordering may use absolute distance to today, with missing/invalid dates marked unknown; no automatic selection follows from sorting. Preserve explicit historical references and separate record creation dates from event dates. Do not invent a timezone or convert ambiguous source times.

One logical profile, built with existing types and orchestrator. Fetch authorized overview sections on entering customer_assistance, overlap independent reads, reuse per-turn caches and completed results, then enrich likely relevant records with existing bounds/deadline/visited set. Do not recursively fetch every historical record. Retain summaries and IDs for unexpanded records so they remain retrievable. No second profile-generation model call. Subsequent writes invalidate affected profile sections and use fresh verified outcomes.

Use existing section status/completeness fields: ready, not_found, not_requested, unavailable, failed and partial must remain distinct. “No other records” is permitted only for the stated scope when relevant sources succeeded and their pagination/history coverage establishes exhaustion. One empty route does not prove global absence. Missing alternative capability means unavailable, not empty.

## Packet P1 — canonical profile and lookup reuse

Owner: runtime worker. Files: src/runtime/customer-context.ts, src/core/information.ts, src/runtime/information-orchestrator.ts, src/runtime/agent-service.ts; tests/l4-customer-context.test.ts, tests/l4-customer-context-service.test.ts and existing information-orchestrator tests.

Move profile initialization from reply-only recovery to customer-assistance entry before reference resolution needs the evidence. Preserve the existing owner router; do not prefetch customer data for a pure public FAQ or planning-only turn. Reuse the same snapshot through resolution and reply. All authorized lookup results enrich this snapshot, whether sourced by phone, account, purchase detail or event detail.

Merge records only by compatible stable IDs and access scope. Cross-route name equality alone is not identity. Preserve provenance/fetchedAt and field conflicts; authoritative detail supplies missing fields, but conflicting fresh records remain explicit until resolved. Orders, gifts, carts, events and guest attendance remain distinct linked entities. Same event with different guests never shares an attendance slot.

Keep one canonical copy of each fact. Existing information execution summaries may retain operation/result status and references for audit, not a second customer-data payload. Customer profile contains facts and coverage; action receipts remain typed outcomes, not suggested prose.

Acceptance: duplicate route results coalesce without losing detail; repeated scoped lookup is performed once per turn; failed route cannot erase known data or assert absence; conflicting guest/event identity does not merge; authorization changes cannot reuse broader cached access; read-after-write refresh is observed. Bounds produce partial completeness, never exhaustive claims.

## Packet P2 — contextual reference inference

Owner: runtime worker, after P1. Project campaign messages with existing provenance: same conversation/customer, outbound direction, delivered status if known, timestamp, and existing structured event association or model-extracted reference. Unknown delivery remains uncertain. Inbound text claiming to be a campaign never acquires outbound authority. Do not invent a backend campaign parameter; reuse current message envelope.

Supply compact profile candidates, active requested aspect, prior referent and relevant campaign context to the existing extraction call. Reuse existing eventHint/rsvpEventReference/candidate fields rather than add a second selector. Ground IDs against profile evidence. Preserve date/time intent in “and the other wedding?” without replaying requests on thanks. Replace campaign-only clarification rules and explicit-hint-only hydration gating with the validated inferred target. Delete superseded logic instead of layering exceptions over it.

Remove fixed ranking weights as a conversational authority; if retained solely for presentation, document that role and order by actual temporal proximity without filtering. Do not persist an inferred read target as consent to a later action.

Acceptance matrix: campaign A→vague date question answers A; explicit B overrides A; nearer B without explicit/campaign focus can be inferred for read-only query; explicit years-old A is retained; conflicting campaigns yield useful distinctions; acknowledgement does not restart work; multiple requested topics survive extraction; recency alone never triggers mutation. All use complete conversation histories.

## Packet P3 — one compact model profile, useful complete answers

Owner: runtime worker, after P2. Files: src/runtime/openai-agent-runtime.ts, src/runtime/customer-context.ts, src/runtime/purchase-reply-projector.ts, src/runtime/reply-evidence-projector.ts, src/runtime/prompt-loader.ts, src/runtime/prompt-manifest.ts; resolver system/response_contract, RSVP response contract, shared question strategy/output style.

Replace overlapping customer facts in information_results and rsvp_phone_evidence with references to the canonical customer_context when that profile is present. Preserve independent effect/outcome facts and operational provenance. Do not blindly delete these blocks on owners that still need them; move their consumers onto the canonical representation in the same change, then remove old serialization, with no compatibility shim.

Expose compact summaries of all available candidates and full authorized detail for the resolved/relevant records. Use stable field ordering and omit duplicate/null-value noise, while retaining explicit section availability. Preserve dates, venue/address, state, amounts and their provenance when useful. Reuse native image references; no image describer or separate stored transcription. Do not change image retention in this packet.

Replace strict “only explicitly requested fields” response policy with useful related completeness. Remove automatic clarification whenever an ambiguity flag exists if actual context resolves it; remove forced currency/balance caveats unrelated to the task and hard paragraph/wording requirements. Do not add an exhaustive list of exceptions. The model must answer every requested part, use tools for available facts, and only ask for information necessary to proceed.

Acceptance: actual serialized requests show customer facts once, zero extra model passes, useful adjacent details available, no new unrelated histories or tools. Record instructions/input/tools/schema bytes and cached tokens on matched scenarios. Profile may be richer than before; do not reject necessary facts to meet an arbitrary byte target. Duplication and instruction overhead must fall, with any necessary input growth explained.
