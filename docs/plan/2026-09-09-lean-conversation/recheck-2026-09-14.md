## Reproduced defects and implications

**D1 — Fixture history is still disconnected.** `src/lambda/handler.ts:getFixtureRuntime` constructs `FixtureAgentConversationGateway.create(scenario)` without run/case/store options. The gateway defaults to local-run/local-case and a new in-memory store. A synthetic receipt produces one message in the first instance, zero in a recreated instance. `recordOutboundReceipt` appears in source only at its declaration; callers exist only in unit tests. The new durable store implementation is therefore not evidence of Lambda continuity. The fixture quote gateway also uses scenario-derived identity instead of actual run/case identity. Do not solve this by globally caching a gateway; that leaks history/effects between cases.

**D2 — History fallback still misses the failure that motivated it.** `applyLastOutboundFallback` returns immediately if there is any recent message. A 2020 campaign prevents inclusion of a September 14 latest reply. Its injected fallback has id -1 and loses original message linkage, truncation and delivery provenance in the generic history shape. This can make incomplete/constructed content look like a complete sent answer. Several branches update last_outbound_context individually, but the public handleTurn wrapper simply returns handleTurnCore, so there is no single guarantee that every normal planning/RSVP exit records the same evidence.

**D3 — Pending-question loss is possible after failed delivery.** In replyOnEstablishedImageNode, consumedPendingQuestion becomes true after composition. Rendering happens later and can return a failure (for example origin mismatch); the plan then clears the question because consumedPendingQuestion is true. A successfully generated clarification can also clear a question it did not answer. Existing comments saying failure paths never clear it are stronger than the implementation.

**D4 — New diagnostic data escapes the redaction boundary.** projectSafePlan spreads the plan and does not override image_attachments or last_outbound_context. A synthetic file ID and email inside last response both survive unchanged. buildLambdaResponseBody includes that projection in diagnostic responses; the live target stores a projected plan too. This is an observed diagnostic/artifact exposure, not a claim that those fields are sent as customer conversation prose. Keep private runtime state intact while closing the public projection.

**D5 — Silence proof accepts an unrelated old image.** validateImageOnlySilence accepted a synthetic turn with a new unavailable image, image_file_silence trace and only an OLD-IMAGE reference. hasSuccessfulImageRefSave checks for any nonempty file/url/message identifier, not linkage to this invocation, active reference or valid current input. It also accepts several legacy aliases instead of the current typed schema. This can make lost input look like successful persistence.

**D6 — The origin verifier can validate its own corrupted renderer.** A model snapshot containing only “Synthetic model sentence.” plus an injected renderer that appends a second runtime sentence results in status verified with no mismatch. The same renderer constructs delivered and expected text. This probe is a fault-injection result, not evidence of an existing canned extra sentence in the production renderer. It demonstrates that the anti-replacement acceptance test is incomplete. Provider metadata validation is separately important; do not disable card rendering to fix this.

**D7 — Error handling remains asymmetric.** Retained-image branches now require an image-access failure; current-image branches still permit isModelStageFailure, including ModelComposedFailureError and broad API names. A generic model/schema failure can still be relabeled image_unavailable. The failed transport metrics are merged, but reply token usage is left untouched. If the failed request supplies no usage, record unavailable rather than invent zero or claim complete token accounting.

**D8 — The lean projection still gives the model conflicting directions.** The purchase operational note contains a prescribed “monto [valor] mediante [método registrado]” fragment and broad instructions to repeat validation context. composeReplyInput emits customerContext in canonical evidence and again in a separate JSON block. The worker log's “one occurrence” counts only one presentation style; the serialized request contains two. Prompt-byte assertions were treated as a reason to leave prescriptions intact; a size pin is a measurement, not authorization to preserve conflicting policy.

**D9 — Image presence is incorrectly used as cart relevance.** deriveCustomerProjectionFocus defines cartSignal as imageAvailable OR supportContinuation OR voucherReport. The probe for payment_status plus an image returns general, not payment. General projection can include unrelated cart information, directly opposing the receipt example and agreed behavior. Cart relevance must come from the user's structured task, never the transport being an image.

**D10 — Profile assembly is wired, proactive bounded enrichment is not.** resolveCustomerContextForReply synchronously assembles already-completed informationResults. assembleCustomerContext is a pure assembler. This does not implement the earlier Packet C requirement to follow authorized order/item/event/venue details with a two-edge/four-read/deadline bound before the owner answer. Existing per-request parallelism is not that graph expansion. Do not call the whole profile feature complete merely because a projector has a caller.
